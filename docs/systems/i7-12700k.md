# Intel i7-12700K

The machine PPE is developed on, and the reference every example in these docs
comes from. Every figure below was produced by the tools in this repository and
is labelled **measured** or **claimed** — the distinction the whole project is
organised around.

Reproduce with:

```bash
cmake --preset release && cmake --build --preset release
taskset -c 4 ./build-release/tools/tool_topology --ascii --measure
taskset -c 4 ./build-release/applications/app_layer_bandwidth --threads 1
taskset -c 4 ./build-release/applications/app_roofline
```

`taskset` is not optional on this part. It is heterogeneous, and an unpinned run
describes whichever core type it happened to land on.

## Topology

Alder Lake: eight performance cores with private L2, and four efficiency cores
sharing one L2, under a single L3.

```
12th Gen Intel(R) Core(TM) i7-12700K
  1 package(s), 12 physical cores, 20 logical processors, 1 NUMA domain(s)
  cache line 64 bytes, topology via sysfs

+-- 8 x cluster  [performance]
|      1 core(s), 2 thread(s)
|      L1d 48 KiB     (private)
|      L1i 32 KiB
|      L2  1.25 MiB   (private)
|      capacity 45 (acpi_cppc)
|
+-- cluster  [efficiency]
|      4 core(s), 4 thread(s)
|      L1d 32 KiB     (private)
|      L1i 64 KiB
|      L2  2 MiB      (shared by 4 cores)
|      capacity 27 (acpi_cppc)
|
\-- L3  25 MiB (shared by 12 cores)
```

A cluster here is *the set of cores sharing one L2 instance*, so each P-core is a
cluster of one and the four E-cores are a cluster of four. `capacity` comes from
ACPI CPPC `nominal_perf`, since `cpu_capacity` is an ARM/EAS file and absent on
x86.

## Clock and issue width — both measured

| | performance core | efficiency core |
|---|---|---|
| sustained clock (perf_event) | **4.949 GHz** | **3.79 GHz** |
| claimed max (cpufreq) | 5.000 GHz | 3.800 GHz |
| FMA units (measured FMA/cycle) | **2** | **1** |

Two things worth noting. The P-core does not quite hold its advertised ceiling
under load, and the E-core does. And the FMA width differs by 2x between core
types — `peak.hpp`'s default of 2 is right for one and wrong for the other.

Together these were a **2.66x error** on E-core peak before both were measured:
the old model used cpu0's claimed 4.9 GHz with an assumed 2 units, reporting
78.4 GOP/s fp64 where the truth is 29.5.

## Memory hierarchy — measured

Latency by dependent pointer chase, bandwidth by streaming read, both pinned.

### Latency

| level | P-core | E-core |
|---|---|---|
| L1d | 1.02 ns | 1.05 ns |
| L2 | 3.7 ns | 7.5 ns |
| L3 | ~15 ns | — |
| DRAM | 75–83 ns | 82 ns |

The E-core's L1 is *faster in absolute terms* — a 3-cycle L1 at 3.8 GHz beats a
5-cycle L1 at 4.9 — while its L2 is twice as slow. No single-valued machine model
shows that.

### Bandwidth, one pinned P-core

| layer | read GB/s | B/cycle | write GB/s | copy GB/s |
|---|---|---|---|---|
| L1d (24 KiB) | 161.8 | 32.3 | 132.0 | 374.6 |
| L2 (640 KiB) | 115.1 | 23.0 | 71.9 | 99.3 |
| L3 (12.5 MiB) | 71–75 | 14.2–15.1 | 65.1 | 50.3 |
| DRAM (100 MiB) | 28.0 | 5.6 | 16.9 | 44.4 |
| storage | 0.199 | — | — | — |

Aggregate across 8 P-cores: L1d 759 GB/s, L2 332, L3 274, DRAM 66 — the private
levels scale with cores, the shared ones saturate.

The L1d **copy** figure exceeds what the compiled loop can issue because glibc's
`memcpy` dispatches on the runtime CPU and uses wider instructions than the build
ISA allows. Write and copy count the bytes the program moved (STREAM convention);
on a write-allocate machine the DRAM rows move about twice that.

**L1d read needs a settled machine.** Under load it reports 30–60% spread and the
tool marks it `UNRESOLVED`; the figure above is from runs at ~1% spread. The
first sample of any sweep is also elevated — a cold-start effect present
regardless of implementation.

## Roofline, pinned P-core

```
clock       : 4.949 GHz (perf_event) -- MEASURED sustained clock
fma units   : 2 (MEASURED: 1.818 FMA/cycle)
bandwidth   : 27.86 GB/s (MEASURED)

type         peak GOP/s    ridge (op/byte)
fp64               79.2               2.84
fp32              158.4               5.68
int32              79.2               2.84
```

Every input is now derived from the ISA or counted on the hardware. A kernel
below 2.84 fp64 operations per byte moved is memory bound on this machine.

## Storage

```
io mode : O_DIRECT (cache bypassed)
block              seq GB/s  rand latency us
4 KiB                 0.057          6917.79
64 KiB                0.184          7103.18
1 MiB                 0.198         11605.64
```

Sequential reads plateau at ~199 MB/s from 64 KiB upward; below that per-request
overhead dominates. Random 4 KiB latency is ~6.9 ms and queue depth scales only
~2.4x to depth 16. **This is rotating storage**, correctly characterized — an
NVMe device would show sub-100 µs latency and scale into the tens.

## Network, loopback

```
message            RTT (us)      stream GB/s
64 B                  15.01            0.023
4 KiB                  8.75            1.269
32 KiB                16.93            6.146
256 KiB               58.99            9.980

conns        aggregate GB/s      vs 1 conn
1                     6.477          1.00x
8                    22.870          3.53x
```

Loopback is protocol processing plus a memcpy — it never reaches a wire. It
bounds what local IPC over TCP can achieve and says nothing about a NIC.

## Accelerators

```
+-- [GPU] Intel GPU [8086:4680]  (via i915)
|      clock 1500 MHz
|      note: GT clock 300-1500 MHz; execution-unit count is not published
|            by this driver (needs Level Zero)
```

Integrated Alder Lake graphics. No discrete GPU, and no KPU — pass
`--kpu-config` with a kpu-sim system configuration to characterize one.

## Environment caveats

- **`perf_event_paranoid` must be 2 or lower** for the measured clock, FMA width
  and profiler. This machine ships at 4, which denies them; the tools fall back
  to claims and say so. `sudo sysctl -w kernel.perf_event_paranoid=2` enables
  them for the current boot.
- **Hyperthreading is on.** Pinning to a logical CPU leaves its SMT sibling free
  to run other work, which is one source of the L1d read variance above.
- Figures were taken with the desktop otherwise idle. They are a property of this
  machine and this configuration, not of the part number.
